### 1-3. 誤公開・CI 失敗時の公開を防ぐ仕組み

- 本番へ出る経路は Deploy production だけ（`docs/SECURE_DEPLOYMENT_POLICY.md`）
- `workflow_run` での起動は、main への push で Validate site が成功したときだけ。手動実行と定期実行も main でしか動かない（`if:` 条件）
- 公開の直前に、出す版が最新の main であることを確かめる（ビルド中に main が進んだら止める）
- 定期・手動実行では、出す版が Validate site（main）に合格していることを API で確かめる
- 公開後に本番の `/build.json` と出した SHA が一致することを確かめる
- main の保護（ルールセット「Protect main」）
  - PR が必須
  - 必須チェックは `build` と `Analyze JavaScript/TypeScript`
  - 強制 push・削除・非線形履歴は禁止
  - 例外として通れるアカウントは無い
- `prepare-generated-files` は main では動かない（`if: github.ref != 'refs/heads/main'`）
- 注記：必須チェックは「PR ブランチが最新の main を取り込んでいること」を求めない（strict: false）。それでも main への push ごとに Validate site が走り、成功しないとデプロイされないので、組み合わせの不具合が本番に出ることはない

### 1-4. ロールバック・復旧

`docs/ROLLBACK_RUNBOOK.md`（10/28 更新）は Actions だけを経路にする方針と合っている。

- 基本は「原因 PR を revert する PR → CI → マージ → Deploy production」
- Cloudflare の画面での切り戻しは非常時だけ。その場合もすぐ revert の PR で main を本番に揃える
- 手元からの `wrangler deploy`・`wrangler rollback`・`npm run deploy` は禁止と明記されている

- `/control/` は認証で守られている
- `/preview/` と `/seo-changes.json` は、AI クローラーには取得を許したことになる
- 個別グループにも同じ Disallow を書くのが安全
