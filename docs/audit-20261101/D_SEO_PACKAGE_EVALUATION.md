- 観測窓：`npm run growth:check -- <path> --type metadata`（11/01 実行）
- 期待増分 views は**推測**
  - 計算：28日の表示回数 ×（目標 CTR − 現在の CTR）× 1.15（直近28日の views/session）
  - 順位が変わらない前提。目標 CTR はその順位帯で現実的な値に置いた（Gemini の目標値は使っていない）
- ここにある変更はどれも**未実装**。実装はオーナー承認後に Draft PR で行う

- **11月 100,000 views との距離**

  - 6パッケージで採用を推奨するものを全部足しても、増分は**月 +500〜1,300 views 程度（推測）**
  - これらは信頼と事実の正確さを守る施策で、目標との差（約8万）を埋める手段ではない
  - 差を埋める見込みのある需要の発掘は、Growth OS の Recovery の側で別に扱う必要がある

## 4. 効果検証の設計（変更が承認・公開された場合）

既存の仕組みに乗せる。新しい有料ツールは使わない。

| 記録・取得する項目 | 置き場所・取得元 | 状態 |
|---|---|---|
| 対象 URL・変更日・commit SHA・狙うクエリ | `src/data/seo-changes.ts`（1変更＝1エントリ。id は後から変えない） | 既存 |
| 変更前後の title・description | **提案**：`seo-changes.ts` に任意項目 `titleBefore`・`titleAfter`・`descriptionBefore`・`descriptionAfter` を足す（変更の事実なので、この台帳の方針に合う） | 未実装（承認後） |
| GSC のクエリ・表示回数・クリック・CTR・順位 | Apps Script が `seo-changes` の変更日を起点に「変更前7日・変更後7日・変更後28日」を GSC から取り直す（既存の設計） | 既存。7日後と28日後の確認はこの区切りで行う |
| GA4 の Views・Views/session | `performance-snapshot.json`（サイト全体は日次の Google API、ページ別は ChatGPT 側の Windsor） | ページ別は重点 38 ページだけ |

**判定の注意**

- metadata 変更の観測窓は原則14日。7日後は途中経過として見るだけで、成否は28日後に判定する
- 紅葉・試合・イベントは季節で表示回数そのものが動く。変更前後の単純比較では判定しない。同じ期間の、変更していない同種ページ（例：花貫）と比べ、CTR と順位を分けて見る
- 表示回数が少ないページ（28日で 200 未満）は、母数不足として判定を保留する
- 依頼書の目標（スタジアム CTR 5%、観戦 4%、Views/session 1.35〜1.50）は検証用の仮説として記録する。順位帯から見て、スタジアム（8位前後）の 5% と観戦系の 4% は高すぎる可能性がある（推測）

**課題（提案）**

- ページ×クエリの GSC 値は、日次の自動取得（日付別の合計だけ）に含まれていない
- 対象 URL の分だけ `scripts/google-api-daily.mjs` で取得するように広げれば、GSC API の無料の範囲で 7日・28日の判定を自動化できる
- ワークフローとデータの変更なので、オーナー承認が要る
