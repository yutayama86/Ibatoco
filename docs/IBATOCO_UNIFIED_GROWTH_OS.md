# Ibatoco Unified Growth OS

最終更新: 2026-10-25

## 目的

イバトコの運営を、以下の3層で一本化する。

1. **このChatGPTスレッド = 司令塔**
   - オーナー判断、優先順位変更、新規アイデア、例外判断を受ける。
   - ここで確定した重要判断は、必要に応じてGitHubの正本へ反映する。
2. **/control/ = 可視化・判断画面**
   - GA4/GSC/収益/イベント/実装キューから、勝ち筋・改善点・重点ページ・次の一手を表示する。
   - 数字の閲覧ではなく「何をするか」を決める画面とする。
3. **毎朝7時の統合Growth OS = ChatGPTの日次運用**
   - Control CenterとGitHub正本を読み、最も期待値が高い施策を選ぶ。
   - 実装できるものは ChatGPT が branch → implementation → PR → CI まで進める。merge → Deploy production → production verify は、オーナーが対象PRを明示的に承認した後に行う。

## 唯一の運用正本

判断時は以下を優先順で使う。

1. オーナーの最新確定判断
2. この文書
3. `docs/prompts/IBATOCO_DAILY_GROWTH_DIRECTOR.md`
4. `docs/EDITORIAL_OS.md`
5. `docs/REVENUE_OS.md`
6. `docs/IBATOCO_MASTER_STRATEGY.md`
7. `data/editorial/action-queue.json`
8. `data/editorial/performance-snapshot.json`
9. その他の自動生成レポート

矛盾時は新しいオーナー判断を優先し、古いルールを復活させない。

## オーナー最上位経営判断（2026-10-11）

**最終目的はオーナー自身が圧倒的に稼げる事業を構築すること。** イバトコに関わる読者・地域事業者・働く人の豊かさを増やし、その価値創出の中枢としてオーナーに十分な利益・持続的な事業資産が残る構造をつくる。地域貢献だけで終わる無収益施策は事業戦略の中心に置かない。

**実行順位は短期SEO最優先**。2026年11月のGA4 Views 100,000達成に向け、検索需要の獲得を最優先しながら、編集・SNS・地域連携で未顕在需要を創出する。SEO集客と需要創出を切り離さず、検索で獲得した読者を地域の新しい体験・店・サービスへ誘導する。

**収益設計は集客と同時進行**。宿泊・体験等の承認済み送客、事業者のWeb/SNS/SEO・予約CRM継続支援、協賛・地域データ等を、検索意図と事業者価値が合致する場面で検証する。価格・新規契約・広告出稿・有料サービス導入は従来どおり事前承認。広告掲載と編集推薦を分離する。

判断・日次報告では「Viewsの増分見込み」と「オーナーに残る確定粗利益・継続収益・再現可能な資産」を分けて評価する。優先指標は **確定売上、粗利益（計測可能な場合）、オーナーの実質取り分、MRR、Revenue/1,000 Views、B2B有料受注、確定送客成果、Founder dependence**。未計測はnullで扱い、クリック・問い合わせを売上に換算しない。11月Views目標を理由に短期利益だけへ偏らず、信用・一次情報・読者体験を維持する。

実装体制は **ChatGPTがGrowth Director兼原則の実装担当**。GitHub確認・編集・PR・CI・本番検証をChatGPTで進め、Claudeへの開発依頼はオーナーが別途指示した場合のみ行う。

## 運用体制（2026-10-25 オーナー決定）

毎朝の Claude Code 自動実装（PR #421 で導入した `daily-claude`）は、設定・認証・保守の負担が大きいため運用を中止した（ワークフローは無効化済み）。日次運用は ChatGPT で完結させる。

| 担当 | 範囲 |
|---|---|
| ChatGPT | 毎日の GA4/GSC 分析と Growth 戦略、ニュース・イベントの一次情報調査、記事の制作・更新・校閲、SEO 改善・内部リンク・軽微な修正、GitHub の PR 作成と CI 確認、オーナー承認後のマージと本番公開の確認、SNS 投稿原稿、収益・セキュリティ状況の確認 |
| Claude Code | 大規模な Astro 改修、複雑な不具合修正、多数のファイルを対象とする変更、高負荷・長時間の開発。いずれも ChatGPT またはオーナーから明示的に依頼された場合だけ |

- Claude Code を定期的・自動的に起動しない。依頼は必要なときだけ手動で行う。
- 毎日のニュース記事は ChatGPT が制作し、PR を作成する。
- 本番公開は、対象PRごとにオーナーが明示的に承認した後だけ（PR→CI→承認→マージ→Deploy production）。
- 追加課金をしない。
- メルマガ原稿の作成は廃止した。
- 協賛の営業活動は引き続き停止する（再開・提案先・価格はオーナー判断。`docs/REVENUE_OS.md`）。

## メディア主導の高収益事業方針（2026-10-11 オーナー最新判断）

**イバトコ自体を圧倒的に稼げるメディア・地域取引基盤に育てる。** Web制作・SNS運用の受託会社へ転換することは目的としない。B2B受託は当面のキャッシュ創出や顧客課題の検証に役立つ場合のみ補助的に扱い、主力の資源配分を奪わせない。

- 最優先の集客KPIは2026年11月GA4 Views 100,000。これと並行して、読者の「知る→比較する→行く/泊まる/予約する/買う」の行動を実際の収益へ接続する。
- 優先収益レーン（2026-10-13 オーナー決定で順番を変更。詳細は `docs/REVENUE_OS.md`）は、①地域事業者からの継続収益（明示された協賛/スポンサー、店舗・施設の有料掲載、送客成果報酬）②承認済みアフィリエイト（楽天トラベル・じゃらん・akippa 等）③再利用可能な地域情報・集客データと予約基盤。Web制作・SNS運用の受託は補助。独自予約・決済・取引手数料は提携契約、権利、個人情報、決済/取消運用を確認するまで構想に留める。
- 44市町村・イベント・店舗・体験の一次情報を検索、推薦、回遊、将来の送客商品に再利用できる資産として整備する。情報提供と有料掲載の境界を明確にし、編集推薦順位は販売しない。
- North Starの最終経営目標は**2027年9月時点でオーナー個人が税引後年1億円を継続的に得られる収益力**。これは挑戦目標であって達成予測ではない。売上/利益/個人手取りを区別し、仮定の転換率や取引額を実績として記録しない。
- **自己資金50万円未満**を前提に、退職・法人化・固定オフィス・正社員採用を先行させない。初期は既存基盤/無料枠/受注後外注で検証し、継続的な確定利益と資金余力を確認してから拡張する。
- Growth施策の評価は Views・商用意図・有料送客率・確定成果・Revenue/1,000 Views・粗利益・MRR・運営工数・データ資産性。クリックや問い合わせを確定売上に算入しない。
- 新規ASP契約、価格/有料掲載条件、決済、個人情報取得、外部課金、公開UIの大幅変更は従来のオーナー承認ルールを維持する。

## North Star

短期（最優先）:
- 2026年11月 月間GA4 Views 100,000
- 低品質量産ではなく、検索需要・回遊・高意図導線を伸ばす。

中期・長期（2026-10-25 オーナー確認。段階の詳細は `docs/IBATOCO_MASTER_STRATEGY.md` の二層成長ロードマップ）:
- 中期：月間100万PV
- 長期：2027年12月までに月間200万PV

事業:
- 確定売上
- Revenue / 1,000 Views
- B2B問い合わせ
- 継続収益比率
- Founder dependence低下
- 再利用可能な地域データ資産

PVだけを増やして収益・資産性・信頼性を壊す施策は禁止。

## 先回りの原則（2026-10-07 オーナー判断）

11月100,000 Viewsを最優先KPIとしつつ、単月だけを目的にせず「今年の実測を蓄積し、2027年以降の検索需要を先読みできるメディア」をつくる。記事本数はKPIにしない。

笠間新栗まつりの終了後、流入の落ち込みにオーナーがGA4で先に気づいた。今後は「流入が落ちてから気づく」状態を禁止し、Growth OS 側が次を先に判断する。

- 今の勝ちページがいつ失速するか、何PV失う可能性があるか（**PV at Risk**）
- そのPVをどの次の山へ渡すか（**PV Relay**：新栗 → コキア → 土浦花火 → 紅葉 → 大洗あんこう → 12月 → 年末年始 → 初詣 → 梅 → 桜）
- 次に検索需要が上がるテーマ（**Demand Radar**。大きさより増加速度を重く見る）
- 何日前までに仕込むか（**30/60/90日 Pipeline**。10月時点で1月需要まで、11月に入ったら1〜2月まで）
- 既存記事の改善と新規記事のどちらが期待値が高いか（期待追加PV ÷ 工数）
- 2026年の季節実測を2027年の公開・更新時期に使う（**Annual Learning**。同カテゴリ2件以上の実測がそろうまで推測で変えない）
- 収益は PV → CTA表示 → CTAクリック → ASP送客 → 発生成果 → 確定成果 → Revenue に分け、クリックを成果として扱わない（**Revenue Funnel**。A8 は「クリックあり・成果0」）

計算と表示の正本は `docs/GROWTH_ENGINE.md` の 8〜12.。日次の見方は `docs/prompts/IBATOCO_DAILY_GROWTH_DIRECTOR.md` の「Demand Radar / PV Relay」（12項目）。実測できない値は null、予測は forecast として扱い、実測として保存しない。

## Control Centerと実行キューの関係

### 10万PV Recoveryの終了条件（2026-10-09 オーナー判断）

目標は**2026年11月1〜30日のGA4 Views 100,000**。ローリング28日は補助指標であり、10月の実績を11月の達成PVへ加算しない。

- `data/editorial/recovery-plan.json` を毎回読み、未達ペースなら需要獲得と資源配分を組み替える。新しいOS・機能の追加だけで日次Growth完了にしない。
- Growth Engineの直近7日×30日と、最新3日×30日は**現状ペースの参考値**。季節需要を含むportfolio予測、保証下限、達成確率とは別物。前週比プラスでも最新3日が減速していれば両方を報告する。
- 11月portfolioはページ/検索意図の重複を除いたbase・追加Views・根拠・確度・公開期限・実行状態を記録する。再現可能な根拠が無い増分はnullのまま。未知の需要を「0」とも「獲得予定」とも扱わない。
- 参考値で不足が数万PVあるのに、小さなCTR修正数件だけで埋まると判断しない。少なくとも週2回、GSC未露出需要を一次情報・市場根拠から探索し、11月の重点クラスターと既存流入からの配信・回遊を比較する。
- Today's Growth Batchの表示は候補。観測窓中、実装仕様未完成、未確認の事実、将来の公式発表待ちは即実装しない。実行可能な代替へ再選別する。実装0件の日は0件と報告し、解除条件と次の一手を記録する。
- Growth/Revenue/Maintenanceの成果を区別する。データ同期・正本整備・Control改修・監査完了を「獲得したPV」と計上しない。追加Viewsを見積もれなくても、必要な事実更新を候補から排除しない。
- 10/12・10/19・10/26に需要と着地見通しを再判定。根拠付きの確度補正portfolioが目標の120%以上になるまでRecoveryを維持する（管理バッファであり達成保証ではない）。
- 追加機能・LocalOS拡張・全面デザインは未達対策と比較して原則保留。既存の予約送客MVPとB2B自然流入の検証は継続する。10万PVを待たず確定売上を追い、クリック・フォーム送信を受注と扱わない。

既存の追加費用ゼロ・公開許可範囲・観測窓・Responsive QAは変更しない。Recoveryの候補が人気順位の実測を上書きしてはいけない。

数値の計算（11月の着地予測・Gap・ページ別予測・SEO機会・季節の締切・観測窓・施策の優先度・期限切れ/年度チェック）は Growth Engine（`docs/GROWTH_ENGINE.md`）を正本とし、Control Center と日次レポート（`npm run growth:target`）が同じ式を使う。変更前の観測窓の確認は `npm run growth:check -- <path> --type <種類>`。

Control Centerの表示は3種類に分ける。

- **判断**: 勝ち筋、改善点、リスク、着地予測、PV at Risk、Demand Radar、Next Winners
- **候補**: 重点ページ、SEO機会、収益機会、30/60/90日 Pipeline、Revenue Funnel、Annual Learning
- **実行状態**: `data/editorial/action-queue.json` の ready / in-progress / done

Control CenterのP1/P2は、そのまま自動実装を意味しない。
毎朝7時OSが、実測・観測窓・一次情報・工数・リスクを再評価し、実行可能なものを action queue の ready / in-progress に落としてから実装する。

## 毎朝7時の終了条件

以下をすべて満たして初めて「完了」。

1. GA4/GSC/収益/台帳/Control Center判断を更新・確認
2. 今日の最重要ボトルネックを1つ決定
3. action queueの状態を整合
4. 実装できるものは ChatGPT が実装
5. PR作成
6. CI成功
7. オーナー承認待ちのPRを、対象・CI・リスクとともに報告
8. オーナーが明示的に承認したPRだけ merge → Deploy production（GitHub Actions）成功 → production verify
9. 検証窓を登録
10. オーナー向け報告

途中で止まった場合は「未完了」とする。オーナー承認待ちのPRは「承認待ち」として報告し、承認なしにマージしない。

## ChatGPTがPR作成まで進めてよいもの（マージはオーナー承認後）

- 一次情報で確定した事実更新
- 内部リンク・関連記事・回遊改善
- metadataの小規模改善
- 高表示低CTRページの小規模スニペット改善
- 終了イベントの表示・推薦除外
- 計測欠落・明白な技術不具合
- 承認済みアフィリエイトURLの既存ルール内マッピング
- Control Center / Operator OS / CIの低〜中リスク改善
- 既存URLを維持するコンテンツ更新
- 実測に基づくpopular-pages/action queue更新

## オーナー承認が必要

- 新規有料SaaS/API/従量課金
- ASP申請・契約・広告出稿・スポンサー契約
- 価格変更
- URL変更・削除・統合・リダイレクト
- 大規模IA/全面デザイン変更
- 個人情報の新規取得
- GA4/GSC ID変更
- 権利・許諾

## 優先順位

通常は以下の順。

1. 誤情報・計測・本番障害
2. 11月大型検索需要
3. 既にGSC露出がある8〜20位/高表示低CTRページ
4. 勝ちページからの回遊
5. 高意図ページの予約/送客/収益導線
6. B2B自然問い合わせ導線
7. Discovery/DB/Owned Audience
8. 新規ニュース・新機能

ニュース本数はKPIにしない。

## 実験観測窓

- 事実/計測不具合: 即時
- CTA/小UI: 7日
- metadata/internal links: 原則14日
- 本文/template/IA: 原則28日
- 季節案件: 開催期限を優先

母数不足で失敗判定しない。同じURLを短期間に重ねて改修しない。
